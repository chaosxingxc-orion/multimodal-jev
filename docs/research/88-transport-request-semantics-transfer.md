# 共同请求规约在交通队列的应用

本轮完整读取282个原生transport_query/transport_ticket学习来源，关联1,232录音。
使用与联系人研究逐字相同、hash相同的
[共同请求规约](../../configs/tasks/intent-request-semantics-candidate-v1.json)，新增
[交通领域定义](../../configs/tasks/slurp/transport-semantic-presence-candidate-v1.json)，
逐来源给出两张定义的564项参考建议。没有重写共同规则来迎合交通gold。

这是同一数据集跨领域的规则适用性研究，不是跨数据集模型迁移成绩。输入仍按未来
音频+任务定义的一次Span消费设计；参考文本仅用于离线任务定义和审核。

## 领域定义与共同逻辑

`travel_information_lookup`覆盖行程路线、距离/时长、时刻、服务可用性、票价、
票务信息和取得车票的方法/地点。单独场所发现或地图显示没有行程信息目的时不归入；
交通接入点如车站位置属于交通信息。这个边界是明确的项目定义，不冒充官方排他类。

`transport_passage_acquire`覆盖购买、支付、预订车票/座位/交通行程。明确的订票请求
即使缺目的地也成立；只有旅行愿望、打开应用、询问票价不等于取得车票。泛称ride
未说明交通服务时可能是出租车；泛称ticket也可能非交通票，均不靠native标签补领域。

共同Q仍然是“是否表达满足所给定义的请求”，领域变化由定义卡承载，不按样本主题
预选问题。信息查询和操作可以并存，但信息需求本身不授权操作；结果不提供真实环境
状态或支付授权。缺标、语义歧义不转换成false。

与旧两卡fit相比30个数值变化：27旧未决变明确（6true、21false），另3旧明确变未决。
旧69个未决在新契约下为45个；这不是把未决率降低作为任务目标，更不是原生纠错率。
`help me book`涉及两项，平台隐含领域涉及一项；它们说明规则收敛也可能撤回旧确定性。
其余534项已重新按新定义判读，不因数值相同就宣称原审核适用于新契约。

## 跨领域得到的结论及限制

联系人16236“查找并添加”、17063“检查后条件添加”和交通12333“预订并问可用性”
都可以用同一个“逐个请求判断、排除不整句否决”规则解释；联系人16621仅添加和发信，
与交通12705只打开应用，则都不能凭执行常识补出未表达的lookup。这支持规约的可复用
设计方向，但还未证明模型能理解它，更未证明过程奖励能提高Final。

两领域合计429来源、858项建议、1,789录音，共享请求政策不变。它们仍来自定向原生
类队列，未覆盖全学习人口中所有潜在联系/交通语义，也没有把其余原生类补为负例。
未进入current workpack正式监督；不以这1,789录音代替40,513全规模学习人口。
