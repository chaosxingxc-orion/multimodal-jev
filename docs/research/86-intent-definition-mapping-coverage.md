## 成对审核揭示的规则问题

联系人147来源对两卡都有审核：67检索支持/修改不支持、34修改支持/检索不支持，
22修改不支持/检索未决、14两者未决、7两者不支持、3修改支持/检索未决。
交通282来源：162查询支持/购票不支持、84查询不支持/购票支持、34两者未决、
1查询未决/购票支持、1两者不支持。这些是旧定义下的拟合矩阵，不是新版多意图标签。

三个具体反例决定下一步的规则工作：

- 12333：`book a ticket ... what is available`。现购票支持、查询未决。
  “排除购票”究竟排除单个购票行为，还是排除整句任何查询，是任务级规则缺口；
  不能用native ticket标签替代这个决定。
- 16236：`look up and add ... to my contacts`。现修改支持、检索未决。
  16621包含添加联系人与发送邮件，却不能因此猜测它明确请求检索。需要按行为目标
  分别判定，不能把所有复合请求机械标成两个都true。
- 17063：`check ... if not then add it`。条件添加的请求可以被表达，但没有证据说明
  条件已满足或添加已执行。请求存在、原生互斥类别与执行状态须分别定义。

本轮不修改这些旧判决。下一次修订应先明确excludes的作用域与条件请求政策，再对
受影响完整来源队列复审；不能把旧unresolved批量转true/false。

## 任务冻结的处理决定

1. **原生Final保持60类。** 此层使用已发布clean标签，不把本轮104个不匹配录音
   宣布为官方错误，不删除、合并类别或改变原生指标分母。
2. **候选定义不可用时，不伪造语义。** cooking_query定义依赖“两条原生样本”，
   general_quirky明确写着未验证的杂项边界；两者目前不具备可迁移定义消费资格。
   该结论不把它们从Final候选中删去，也不允许按样本gold动态隐藏定义。
3. **I_class与I_present不能静默互换。** 当前主任务登记的是互斥类别成员判断。
   如果提供独立语义存在判断，应另行发布明确的I_present定义与监督，并保留native
   Final为独立目标。当前fit结果既不自动授权I_class，也不自动授权新I_present。
4. **先解决可泛化的共同规则。** 联系人、交通等先定义信息获取/状态改变/条件请求/
   并列请求的逻辑边界，之后再处理各领域角色。不能按当前样本主题选择Q，不能按
   原生gold制定主意图优先级。多请求可在语义层共存，不自动证明native选错。
5. **存在性不能硬映射为Final。** 即便未来I_present完整可信，多个true也不提供
   原生单标签的唯一选择规则。Final仍需直接消费音频与任务规约，不用猜出的优先级
   把过程布尔输出强行折叠为gold。

当前有两种需要在任务包中明确区分的契约：原生label-membership由原生完整标签投影，
只检验分类/重编码；可迁移semantic-presence需要新的语义定义及覆盖，检验定义消费。
把前者命名为后者会造成虚假的迁移结论。现有任务v2未在本轮切换；先完成共同请求
语义政策和无法定义类别的处理，再一起定稿算子与菜单，避免工程先行。

这次重建验证全部原始metadata、source target、来源—录音绑定及60类统计；每个录音
仅在其显式所有source ID均有相同fit时归入该状态，不沿source_group传播标签。
新增5项防误准入/缺标/多来源测试，与既有6项相关测试合计11项通过。
独立程序复核不是第二位语义审稿人，正式新增语义监督仍为0；未改actor、训练配置、
当前槽位包或原生数据，未派发模型任务。
