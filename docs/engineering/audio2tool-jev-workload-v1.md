后续正式执行需要分清以下阶段：

1. 完成已排队native NPU容量探测，再用实际全量native运行验证吞吐与截断情况。
   一token容量探测只能证明所选边界可前向，不足以外推完整JSON生成速度。
2. 独立Jev仍需覆盖自己的12个上下文边界及真实生成路径；native容量不能直接
   代替最大18168输入token的Jev容量结果。所有457决策及30733记录保持明确完整分母。
3. 若引入公共前缀缓存、音频处理复用或请求批处理，登记为新的运行配置，先在学习集
   比较同一音频、模板、输出token和错误情况，验证吞吐与结果一致性后再用于全量。
   当前固定native引擎关闭prefix cache，不能把尚未实现的复用当作已有成本收益。
4. 推理账本应使用有界打开文件数和顺序分片，避免给1404万决策各创建两个小文件；
   仍需保留每项实际attempt、terminal、输入身份与原始输出，不静默重放或伪造缺项。

将多个决策打包成一次联合生成会改变条件化方式和输出协议，不能暗中替换已有
独立决策基线或复用其评分承诺；如后续研究该方案，需要独立命名、完整决策映射、
输出容量检查及native配对指标。目前没有派发全量Jev生成、改变数据划分、缩减
评测总体、根据external_test调整RL奖励或宣称学术性能收益。
